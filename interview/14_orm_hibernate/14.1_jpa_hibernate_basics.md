## JPA vs Hibernate

- **JPA** (Jakarta Persistence API) — specification (interface). Defines annotations (`@Entity`, `@Id`, `@OneToMany`), `EntityManager`, JPQL.
- **Hibernate** — most popular JPA implementation. Adds extras: HQL, second-level cache, `@BatchSize`, `@NaturalId`, `Session` API.
- **Spring Data JPA** — abstraction on top of JPA: `JpaRepository`, query derivation (`findByEmailAndStatus`), `@Query`.

---

## Entity Lifecycle States

```
new (transient)
    ↓ persist()
managed (persistent)   ←→ flush() → SQL sent to DB
    ↓ detach() / close session
detached               ← merge() → back to managed
    ↓ remove()
removed                → DELETE on flush
```

- **Transient** — new object, not associated with any `EntityManager`, no DB row
- **Managed** — tracked by current persistence context; changes auto-flushed
- **Detached** — was managed, session closed or `detach()` called; changes ignored unless `merge()`d
- **Removed** — `remove()` called; DELETE pending on flush

## First-Level vs Second-Level Cache

**First-level cache (L1)** — per `Session` / `EntityManager`. Always on, cannot be disabled. Within one session, same entity loaded twice → returned from cache, no second SQL. Cleared on session close, `em.clear()`, or `session.evict(entity)`.

**Second-level cache (L2)** — per `SessionFactory`, shared across sessions. Opt-in, disabled by default. Survives session close.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          region.factory_class: org.hibernate.cache.jcache.JCacheCacheRegionFactory
```
```java
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Country { ... }
```

Concurrency strategies: `READ_ONLY` (immutable), `READ_WRITE` (most common), `NONSTRICT_READ_WRITE` (eventual consistency ok), `TRANSACTIONAL` (JTA only).

Common providers: EhCache, Caffeine (via hibernate-jcache), Redis.
Use for: read-heavy, rarely-changing reference data. Avoid for: frequently updated entities — invalidation overhead outweighs benefit.

### What is the difference between L1 and L2 cache in Hibernate? How do you enable L2 cache?

L1 is per-Session, always on — same entity ID within one session returns from cache, no SQL. L2 is per-SessionFactory, shared across sessions, opt-in via config + `@Cache` annotation on the entity.

**Key points:**
- L1 scope = single session/transaction; L2 scope = application-wide
- L1 always enabled; L2 requires cache provider dependency + `use_second_level_cache=true` + `@Cache` on entity
- L2 concurrency strategies: READ_ONLY, READ_WRITE, NONSTRICT_READ_WRITE, TRANSACTIONAL
- Query cache exists too — caches JPQL result sets, only useful combined with L2

**Common mistakes:**
- Not knowing L2 is disabled by default
- Forgetting `@Cache` annotation on the entity after enabling L2 globally
- Applying L2 to frequently-updated entities (net negative due to invalidation)

**Query cache** — caches the **list of entity IDs** for a JPQL query + parameters. Requires `use_query_cache=true`. Only useful when L2 entity cache is also enabled (otherwise it still fires N SQL to load each ID). Cache region is **invalidated on any write** to the involved table — even one INSERT/UPDATE/DELETE wipes the entire region. Best for near-immutable reference data (lookup tables, configs). Enable per query with `@QueryHint(name="org.hibernate.cacheable", value="true")`.

## EAGER vs LAZY Loading

```java
@OneToMany(fetch = FetchType.LAZY)   // default for collections
private List<OrderItem> items;

@ManyToOne(fetch = FetchType.EAGER)  // default for single associations
private Customer customer;
```

- **LAZY** — proxy returned; SQL fires only when you access the field. Requires open session.
- **EAGER** — always fetched with parent; can cause performance problems (unexpected JOINs).

**Rule of thumb:** always use LAZY, override per query with JOIN FETCH or EntityGraph.

### Why is changing LAZY to EAGER a bad fix for LazyInitializationException?

EAGER is a global change — it applies to every query on that entity, even when the association is irrelevant. The correct fix is to fetch eagerly only in the specific query that needs it.

Problems with EAGER:
- Every `findAll()`, `findById()`, every derived method now loads the association — wasted joins and memory
- On `@OneToMany` collections, EAGER + multiple associations generates a cartesian product in SQL (rows multiply), then Hibernate deduplicates in memory — can easily produce millions of rows
- OOM: loading entire object graphs when you only need parent data

Correct fixes:
```java
// JOIN FETCH for a specific query
@Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);

// @EntityGraph on a specific repository method
@EntityGraph(attributePaths = "items")
Optional<Order> findById(Long id);

// @BatchSize — batches lazy collection loads into one IN query
@OneToMany @BatchSize(size = 50)
private List<OrderItem> items;
```

**Key points:**
- EAGER = global; JOIN FETCH / @EntityGraph = local, explicit, scoped to one query
- Multiple EAGER @OneToMany collections → MultipleBagFetchException or cartesian product
- Keep everything LAZY, fetch where needed

**Common mistakes:**
- Switching to EAGER as a quick fix — it trades one problem for many
- Not knowing @BatchSize as a middle ground for collections that are accessed in loops

### What are the default fetch types for @ManyToOne and @OneToMany? What is the rule of thumb for choosing?

JPA specifies: single-valued associations load eagerly, collection-valued associations load lazily.

| Annotation | Default |
|---|---|
| `@ManyToOne` | EAGER |
| `@OneToOne` | EAGER |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

In practice, override `@ManyToOne` to LAZY and fetch eagerly only where needed using `JOIN FETCH` or `@EntityGraph`. This keeps queries predictable and avoids unexpected joins in bulk operations.

**Key points:**
- `@ManyToOne` is EAGER by default — a common surprise
- Collections (`@OneToMany`, `@ManyToMany`) are LAZY by default
- Rely on LAZY universally; express eager fetching explicitly at the query level
- EAGER on collections is the fastest way to get an accidental cartesian product

**Common mistakes:**
- Assuming LAZY is the default for all associations — `@ManyToOne` catches people off guard
- Leaving `@ManyToOne` as EAGER and then loading 1000 entities, triggering 1000 extra joins
- Not knowing the rule of thumb (always LAZY + fetch per query)

## Cascade Types & orphanRemoval

### What are the JPA cascade types and what does CascadeType.ALL mean? What is orphanRemoval?

JPA defines 6 cascade types: PERSIST, MERGE, REMOVE, REFRESH, DETACH. `CascadeType.ALL` is shorthand for all five. Cascading means the operation on the parent is propagated to associated children.

```java
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
private List<OrderItem> items;
```

`orphanRemoval = true` deletes a child entity when it is **removed from the parent's collection** — even if the parent itself is not deleted:

```java
order.getItems().remove(item);  // item is now orphaned → DELETE fires on flush
```

This is different from `CascadeType.REMOVE`, which only fires when `em.remove(parent)` is called.

**Key points:**
- 6 types: PERSIST, MERGE, REMOVE, REFRESH, DETACH; ALL = all combined
- `CascadeType.REMOVE` cascades `em.remove()` down to children
- `orphanRemoval` fires when child is removed from the collection (parent alive or dead)
- Never use `CascadeType.REMOVE` or `ALL` on `@ManyToOne` — you'd delete shared parents

**Common mistakes:**
- Confusing `CascadeType.REMOVE` with `orphanRemoval` — they overlap on parent delete but differ on collection removal
- Using `CascadeType.ALL` on `@ManyToOne` (cascades remove upward — deletes the parent)
- Forgetting that cascade does not apply to bulk JPQL/native queries, only `EntityManager` operations

## em.persist() vs em.merge()

### What is the difference between em.persist() and em.merge()? When does each throw an exception?

`persist()` takes a transient entity and makes it managed. `merge()` copies state from a detached entity into a managed instance and returns that managed instance.

```java
// persist — for brand-new entities
User u = new User("alice");
em.persist(u);           // u itself is now managed

// merge — for detached entities
User detached = loadedEarlier;
User managed = em.merge(detached);  // detached stays detached!
managed.setName("bob");             // tracked
detached.setName("ignored");        // NOT tracked
```

| | `persist()` | `merge()` |
|---|---|---|
| Input state | Transient | Detached (or transient) |
| Returns | void (same object becomes managed) | New managed object |
| If ID already exists in context | `EntityExistsException` | Updates existing row |
| If entity is in Removed state | — | `IllegalArgumentException` |

**Rule of thumb:** `persist()` for new entities, `merge()` for detached entities received from outside the transaction (REST request body, cache, etc.).

**Key points:**
- `merge()` returns a NEW managed object — the original detached reference stays detached
- `persist()` on a detached entity (has ID, not in context) → `EntityExistsException`
- `merge()` is upsert-like: inserts if no row, updates if row exists

**Common mistakes:**
- Calling `persist()` on a detached entity and expecting it to update
- Continuing to use the detached object after `merge()` instead of the returned managed one
- Not knowing that `persist()` returns void while `merge()` returns the managed copy

## N+1 Problem

**Problem:** load 100 orders → for each order, Hibernate fires a separate SQL to load `Customer` → 101 queries.

```java
// Triggers N+1
List<Order> orders = repo.findAll();
orders.forEach(o -> System.out.println(o.getCustomer().getName())); // LAZY → 1 query per order
```

**Fix 1 — JOIN FETCH in JPQL:**
```java
@Query("SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :s")
List<Order> findWithCustomer(@Param("s") String status);
```

**Fix 2 — @EntityGraph:**
```java
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(String status);
```

**Fix 3 — @BatchSize (Hibernate-specific):**
```java
@OneToMany
@BatchSize(size = 50)
private List<OrderItem> items;
// Hibernate loads items for 50 orders at a time instead of 1 at a time
```

**Fix 4 — DTO projection with JPQL or native query** (avoids loading entities at all):
```java
@Query("SELECT new com.example.OrderSummary(o.id, c.name) FROM Order o JOIN o.customer c")
List<OrderSummary> findSummaries();
```

## @Transactional in Spring

Spring wraps the method in a proxy. On entry: begin transaction (or join/propagate). On exit: commit. On unchecked exception: rollback.

```java
@Service
public class PaymentService {
    @Transactional   // defaults: REQUIRED propagation, rollback on RuntimeException
    public void transfer(long from, long to, BigDecimal amount) {
        accountRepo.debit(from, amount);
        accountRepo.credit(to, amount);  // if this throws → both rolled back
    }
}
```

**Propagation types:**

| Propagation | Behavior |
|-------------|---------|
| `REQUIRED` (default) | Join existing tx; create if none |
| `REQUIRES_NEW` | Suspend current tx; always create new |
| `NESTED` | Save point within current tx |
| `SUPPORTS` | Use tx if exists; non-tx if none |
| `NOT_SUPPORTED` | Suspend tx; run non-transactionally |
| `NEVER` | Throw if tx exists |
| `MANDATORY` | Throw if no tx exists |

**Common pitfall — self-invocation:**
```java
// BROKEN: internal call bypasses proxy → @Transactional on process() has no effect
public void start() {
    this.process();  // not going through Spring proxy
}
@Transactional
public void process() { ... }
```
Fix: inject the bean into itself, or extract to a separate bean.

### By default, which exceptions trigger rollback in @Transactional? How do you change this?

Default: rollback on `RuntimeException` (unchecked) and `Error`. No rollback on checked exceptions.

```java
// Rollback on checked exception too
@Transactional(rollbackFor = Exception.class)
public void transfer() throws IOException { ... }

// Rollback on specific checked exception
@Transactional(rollbackFor = IOException.class)
public void process() throws IOException { ... }

// Prevent rollback on a specific RuntimeException
@Transactional(noRollbackFor = OptimisticLockException.class)
public void update() { ... }
```

Real-world gotcha: a service method that throws `IOException` will silently commit the DB write even if it fails, unless `rollbackFor = Exception.class` is set.

**Key points:**
- Default rollback: RuntimeException + Error; no rollback on checked exceptions
- Change with `rollbackFor` / `noRollbackFor` (or `*ClassName` variants)
- Easy prod bug: forgetting `rollbackFor` on methods that throw checked exceptions

**Common mistakes:**
- Assuming all exceptions rollback — checked exceptions do NOT by default
- Not adding `rollbackFor = Exception.class` on methods that call external APIs (which throw checked exceptions)

## Optimistic Locking with @Version

```java
@Entity
public class Account {
    @Id Long id;
    BigDecimal balance;

    @Version
    int version;  // Hibernate manages: increments on each UPDATE
}
```
On `UPDATE`: Hibernate adds `WHERE version = ?`. If another transaction already updated → 0 rows affected → throws `OptimisticLockException`. Caller must catch and retry.

### When would you use pessimistic locking instead of optimistic locking?

Use **optimistic** when contention is low — conflicts are rare, retries almost never trigger.
Use **pessimistic** when contention is high **and** transactions are short — blocking upfront is cheaper than retry storms.

| Scenario | Preferred |
|---|---|
| Low contention, read-heavy | Optimistic |
| High contention, short tx (e.g. inventory decrement) | Pessimistic |
| High contention, long tx (heavy computation, external calls) | Optimistic (don't hold locks long) |

**Key points:**
- Optimistic under high contention → retry storms, wasted CPU, potential livelock
- Pessimistic with long transactions → holds DB locks too long, kills concurrency
- Transaction length matters as much as contention level
- Spring Data: `@Lock(LockModeType.PESSIMISTIC_WRITE)` on repository method → `SELECT ... FOR UPDATE`

**Common mistakes:**
- Saying "use pessimistic when contention is high" without qualifying transaction length
- Forgetting that optimistic retries must re-read the entity, not just re-run the write

### What are the three PessimisticLockModeType values in JPA and when would you use each?

| LockModeType | SQL issued | Use when |
|---|---|---|
| `PESSIMISTIC_READ` | `SELECT ... FOR SHARE` | You want to prevent writes but allow concurrent reads |
| `PESSIMISTIC_WRITE` | `SELECT ... FOR UPDATE` | You intend to update — blocks all competing locks |
| `PESSIMISTIC_FORCE_INCREMENT` | `SELECT ... FOR UPDATE` + bumps `@Version` | Need to signal a logical change even if entity fields didn't change |

`PESSIMISTIC_WRITE` is the default choice in 95% of cases.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Product> findById(Long id);
```

**Key points:**
- All three release the lock when the transaction ends (commit or rollback)
- `PESSIMISTIC_FORCE_INCREMENT` is useful in aggregate-root patterns where child changes should invalidate parent version
- `PESSIMISTIC_READ` is rarely used — most DBs (Postgres, MySQL) treat it similarly to WRITE in practice

**Common mistakes:**
- Thinking `PESSIMISTIC_READ` blocks all reads — it only blocks *writers trying to acquire a conflicting lock*, not plain reads without a lock

## JPQL vs HQL vs Criteria API vs Native

### When would you use JPQL vs Criteria API vs native SQL?

Use JPQL when the query structure is fixed at compile time. Use Criteria API when the query is dynamic — conditionally adding WHERE clauses or JOINs at runtime without string concatenation. Use native SQL for database-specific features or when bypassing ORM overhead.

| | Use when |
|---|---|
| **JPQL** | Fixed query structure, portable across DBs, readable `@Query` annotations |
| **HQL** | Same as JPQL + Hibernate extras (`NATURAL ID`, etc.) |
| **Criteria API** | **Dynamic queries** — optional filters, conditional predicates, type-safe with Metamodel |
| **Native SQL** | DB-specific features (window functions, CTEs, COPY, MERGE), bulk ops, reporting DTOs |

**Key points:**
- The deciding factor for Criteria API is **dynamic structure**, not complexity
- Derived method names (`findByNameAndStatus...`) become unwieldy → switch to `@Query` with JPQL
- Native SQL bypasses dirty checking and L1 cache — entities loaded via native query are managed, but bulk native updates are invisible to Hibernate
- Specifications in Spring Data JPA wrap Criteria API for composable, reusable dynamic filters

**Common mistakes:**
- Using Criteria API just because a query is "complex" — if it's fixed, JPQL is cleaner
- Thinking native SQL updates are reflected in the L1 cache — they aren't; call `em.refresh()` or `em.clear()`

```java
// JPQL
em.createQuery("SELECT u FROM User u WHERE u.email = :e", User.class)
  .setParameter("e", email).getSingleResult();

// Criteria API
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<User> cq = cb.createQuery(User.class);
Root<User> u = cq.from(User.class);
cq.where(cb.equal(u.get("email"), email));
em.createQuery(cq).getSingleResult();

// Native
em.createNativeQuery("SELECT * FROM users WHERE email = ?", User.class)
  .setParameter(1, email).getSingleResult();
```

## Batch Processing with Hibernate

### What Hibernate properties enable JDBC batching? Why do you need flush() + clear() in a batch loop?

Three properties enable JDBC batching. `flush()` sends buffered SQL to the DB; `clear()` detaches all entities from L1 cache to prevent OOM. Always flush before clear or you discard unwritten changes.

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true   # group by entity type so batching works
spring.jpa.properties.hibernate.order_updates=true
```

```java
@Transactional
public void bulkInsert(List<Record> records) {
    for (int i = 0; i < records.size(); i++) {
        em.persist(records.get(i));
        if (i % 50 == 0) {
            em.flush();   // send batch SQL to DB (still in transaction)
            em.clear();   // detach all entities from L1 cache — prevents OOM
        }
    }
}
```

**Key points:**
- `flush()` = writes pending SQL to DB; `clear()` = detaches entities from persistence context (frees memory)
- Must flush BEFORE clear — otherwise unwritten changes are lost
- `@GeneratedValue(IDENTITY)` disables batching — Hibernate needs the ID immediately after each insert; use `SEQUENCE` strategy instead
- For very large datasets: prefer Spring Batch with `JdbcBatchItemWriter` (bypasses ORM entirely)

**Common mistakes:**
- Calling `clear()` before `flush()` — silently discards changes
- Using `IDENTITY` generation strategy and wondering why batching isn't working
- Not setting `order_inserts=true` — without it, mixed entity types break batch grouping

## Interview Sound Bites

**"What's the most common Hibernate mistake you've seen?"**
> N+1 queries — developers rely on LAZY loading and then iterate collections in a loop. Easy to miss in dev with small data; kills performance in prod. Fix with JOIN FETCH or @BatchSize.

**"When would you bypass Hibernate and write native SQL?"**
> Bulk updates/deletes (Hibernate updates row-by-row), complex window functions, database-specific features like `COPY` in Postgres or `MERGE` in Oracle. Also for reporting queries that return DTOs, not entities.

**"How does @Transactional rollback work with checked exceptions?"**
> By default only on `RuntimeException`. For checked exceptions I add `rollbackFor = Exception.class`. I've been burned by forgetting this in service methods that throw `IOException`.
