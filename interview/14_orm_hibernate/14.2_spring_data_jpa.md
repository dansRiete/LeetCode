## JpaRepository Out of the Box

### What methods does JpaRepository provide and how does query derivation work?

`JpaRepository` extends `PagingAndSortingRepository` → `CrudRepository`. Spring generates all implementations at startup via dynamic proxies.

```java
// CrudRepository
save(entity)        saveAll(entities)
findById(id)        findAll()           findAllById(ids)
existsById(id)      count()
delete(entity)      deleteById(id)      deleteAll()     deleteAllById(ids)

// PagingAndSortingRepository
findAll(Sort)
findAll(Pageable)   // returns Page<T>

// JpaRepository extras
flush()                     // force flush to DB
saveAndFlush(entity)        // save + immediate flush
deleteAllInBatch()          // single DELETE — no entity loading
deleteAllByIdInBatch(ids)
getReferenceById(id)        // returns proxy without SQL — for FK wiring only
```

Query derivation: Spring parses the method name into JPQL. Structure = **subject** + **predicate keywords**.

```java
// Subjects
findBy / readBy / getBy / queryBy / streamBy
countBy / existsBy / deleteBy
findTop3By / findFirstBy

// Keywords
findByName(String n)                      // WHERE name = ?
findByNameAndStatus(String n, Status s)   // WHERE name = ? AND status = ?
findByAgeGreaterThan(int age)             // WHERE age > ?
findByAgeBetween(int lo, int hi)          // WHERE age BETWEEN ? AND ?
findByNameContaining(String s)            // WHERE name LIKE '%s%'
findByStatusIn(List<Status> statuses)     // WHERE status IN (...)
findByEmailIsNull()                       // WHERE email IS NULL
findByNameOrderByCreatedAtDesc(String n)  // ORDER BY created_at DESC
```

When names get too long → switch to `@Query`.

**Key points:**
- Method name is `delete` not `remove`
- `getReferenceById` returns a proxy (no SQL) — only use when setting FK associations, not for reading data
- `deleteAllInBatch` issues one SQL DELETE — much faster than `deleteAll` which loads entities first

**Common mistakes:**
- Calling `remove` — the actual method is `delete`/`deleteById`
- Using `deleteAll` on large tables (loads every entity into memory first)
- Using `getReferenceById` to read data — it throws if entity doesn't exist on first field access

## @Query

Use when derived method name would be unreadable or query is complex:

```java
@Query("SELECT u FROM User u WHERE lower(u.email) = lower(:email)")
Optional<User> findByEmailIgnoreCase(@Param("email") String email);

// Modifying query — requires @Modifying + @Transactional
@Modifying(clearAutomatically = true)   // clears L1 cache after execution — prevents stale reads
@Transactional
@Query("UPDATE User u SET u.status = :status WHERE u.lastLoginAt < :cutoff")
int deactivateInactiveUsers(@Param("status") String status, @Param("cutoff") LocalDate cutoff);
// Returns int = rows affected

// Native
@Query(value = "SELECT * FROM users WHERE email = :e", nativeQuery = true)
User findByEmailNative(@Param("e") String email);
```

---

### What annotations are required alongside @Query for a bulk UPDATE/DELETE? Why?

`@Modifying` + `@Transactional`. `@Modifying` tells Spring Data this is a write query, not a SELECT — without it Spring tries to map the result to an entity and throws. `@Transactional` is required because custom `@Query` methods are not transactional by default.

`@Modifying(clearAutomatically = true)` clears the L1 cache after execution — without it, entities already loaded in the session are stale (Hibernate doesn't know the DB changed).

**Key points:**
- `@Modifying` required for UPDATE/DELETE `@Query` methods; returns `int` (rows affected)
- `@Transactional` required unless the calling service method provides a transaction
- `clearAutomatically = true` prevents stale L1 cache reads after bulk write
- `flushAutomatically = true` flushes pending entity changes before the bulk query runs

**Common mistakes:**
- Forgetting `@Modifying` → exception when Spring tries to return entity type
- Forgetting `@Transactional` → `TransactionRequiredException` at runtime
- Not using `clearAutomatically = true` → reading stale entity state after bulk UPDATE

## Specifications (Dynamic Queries)

### What is a JPA Specification and when would you use it over @Query?

`Specification<T>` is a Spring Data JPA interface wrapping a single Criteria API predicate `(root, query, cb) -> Predicate`. Specifications are reusable and composable with `and()` / `or()` at runtime — use them when query conditions are optional (not all filters always applied).

```java
public class UserSpecs {
    public static Specification<User> hasStatus(Status status) {
        return (root, query, cb) -> cb.equal(root.get("status"), status);
    }
    public static Specification<User> olderThan(int age) {
        return (root, query, cb) -> cb.greaterThan(root.get("age"), age);
    }
}

// Repository must extend JpaSpecificationExecutor
public interface UserRepository extends JpaRepository<User, Long>,
                                         JpaSpecificationExecutor<User> {}

// Compose at runtime
repo.findAll(hasStatus(ACTIVE).and(olderThan(18)));
```

Use `@Query` when the JPQL is fixed at compile time. Use `Specification` when conditions are optional — e.g., an admin search form where the user fills in 0 to N fields.

**Key points:**
- Specification wraps Criteria API — no string concatenation, type-safe
- Composable: `spec1.and(spec2)`, `spec1.or(spec2)`, `Specification.not(spec)`
- Repository must extend `JpaSpecificationExecutor<T>` to use `findAll(Specification)`
- @Query = fixed structure; Specification = dynamic structure

**Common mistakes:**
- Forgetting to extend `JpaSpecificationExecutor` on the repository
- Using Specification for fixed queries where @Query is simpler and more readable
- Not knowing that Specification is just a functional interface around Criteria API

## Projections / DTO Queries

### What is the difference between interface projection and DTO projection in Spring Data JPA?

Both select a subset of columns rather than full entities. Interface projection uses a Spring-generated proxy; DTO projection maps directly to a concrete class via a constructor.

**Interface projection** — Spring generates a proxy at runtime:
```java
public interface UserSummary {
    String getName();
    String getEmail();
}
List<UserSummary> findByStatus(String status);
// SQL: SELECT name, email FROM users WHERE status = ?
```

**DTO projection** — explicit constructor, no proxy:
```java
public record UserDto(String name, String email) {}

// Option 1: JPQL constructor expression
@Query("SELECT new com.example.UserDto(u.name, u.email) FROM User u WHERE u.status = :s")
List<UserDto> findSummaries(@Param("s") String status);

// Option 2: Spring auto-maps by matching constructor param names
List<UserDto> findByStatus(String status);
```

**Dynamic projection** — caller chooses the type:
```java
<T> List<T> findByStatus(String status, Class<T> type);
```

| | Interface projection | DTO projection |
|---|---|---|
| Implementation | Spring proxy | Concrete class |
| Nested relations | Yes (sub-interfaces) | Harder |
| Testing | Proxy harder to assert | Plain object, easy |
| Overhead | Slight (proxy per row) | Lower |

**Key points:**
- Interface projection: no class needed, supports nested projections via sub-interfaces
- DTO projection: explicit, no proxy overhead, easier to test, works well with records
- Both reduce data fetched from DB compared to loading full entities

**Common mistakes:**
- Using full entity loading when only 2-3 fields are needed (wastes memory and DB bandwidth)
- Not knowing that interface projections generate dynamic proxies (can matter for debugging)

## Paging & Sorting

```java
Page<Order> findByStatus(String status, Pageable pageable);

// Caller
Pageable page = PageRequest.of(0, 20, Sort.by("createdAt").descending());
Page<Order> result = repo.findByStatus("PENDING", page);
result.getContent();    // current page items
result.getTotalPages();
result.hasNext();
```

For large tables avoid `OFFSET`-based pagination (slow). Use keyset/cursor:
```java
@Query("SELECT o FROM Order o WHERE o.id > :lastId ORDER BY o.id LIMIT :size")
List<Order> findNextPage(@Param("lastId") long lastId, @Param("size") int size);
```

## Interview Sound Bites

**"When do you use Specification vs @Query?"**
> Specification for dynamic search filters where conditions are optional (e.g., admin search form). @Query when the JPQL is fixed but too complex for method naming.

**"What's the difference between Page and Slice?"**
> Page fires a COUNT(*) query to return total pages/elements. Slice doesn't — just tells you if there's a next page. Use Slice when total count is expensive or irrelevant (infinite scroll).

## @EntityGraph

### What does @EntityGraph do and how does it differ from LAZY/EAGER defaults?

`@EntityGraph` overrides fetch strategy **per query** at the repository method level. LAZY/EAGER are static entity-level declarations that apply everywhere; `@EntityGraph` lets you fetch eagerly only for specific queries while keeping the entity mapping clean (all LAZY).

```java
// Named graph — defined on entity
@Entity
@NamedEntityGraph(name = "Order.withItems",
    attributeNodes = @NamedAttributeNode("items"))
public class Order {
    @OneToMany(fetch = FetchType.LAZY)
    private List<OrderItem> items;
}

@EntityGraph(value = "Order.withItems")
List<Order> findByStatus(Status status);   // items fetched eagerly here only

// Ad-hoc — no annotation on entity needed
@EntityGraph(attributePaths = {"items", "customer"})
List<Order> findAll();
```

`type = FETCH` (default): specified attrs eager, others use declared default. `type = LOAD`: specified eager, others use their annotated fetch type.

**Key points:**
- LAZY/EAGER = static, applies to every query; @EntityGraph = dynamic, per repository method
- Prefer all-LAZY entity mappings + @EntityGraph where needed — keeps fetch behaviour explicit
- Ad-hoc style (`attributePaths`) is simpler; named style reusable across multiple methods
- Generates a JOIN, not a separate SELECT — can cause cartesian product on multiple collections

**Common mistakes:**
- Using EAGER on entities to avoid LazyInitializationException — correct fix is @EntityGraph or JOIN FETCH
- Applying @EntityGraph to two `@OneToMany` collections simultaneously → Hibernate throws MultipleBagFetchException
