# 13.2 — Spring Batch: Batch Processing Workflows

## Questions Covered
- What is Spring Batch and why use it over a plain scheduled service?
- Explain Job, Step, Chunk, ItemReader, ItemProcessor, ItemWriter
- How does chunk-oriented processing work?
- What is JobRepository and why does it matter?
- How do you handle restartability and fault tolerance?
- How do you process large datasets without OOM?
- How do you run jobs in parallel?
- How do you skip bad records vs fail the job?

---
Spring Batch provides several "enterprise" features that would be difficult to build from scratch:

Transaction Management: It ensures that if a step fails halfway through a 1-million-row update, the database doesn't end up in a corrupted or "half-finished" state.

Restartability: If a job fails at row 500,000, Spring Batch records the progress in its metadata. When you restart the job, it can pick up exactly where it left off instead of starting from the beginning.

Chunking & Scaling: It processes records in "chunks" (e.g., 100 at a time). This keeps memory usage low even when processing gigabytes of data. It also supports parallel processing to speed up execution.

Job Metadata: It automatically maintains a schema of tables (prefixed with BATCH_) that track every job execution, start/end times, and status (COMPLETED, FAILED, etc.).

How Remote Partitioning Works
To make this work across multiple instances, you typically need a middleware (like RabbitMQ, ActiveMQ, or Kafka) to handle communication.

The Manager Instance:

Determines how to split the data (e.g., "IDs 1-10,000").

Sends a "Step Execution Request" message to a queue.

The Worker Instances:

Listen to the queue.

Pick up a message, execute their assigned chunk-oriented step locally.

Send a "Reply" message back to the Manager once finished.

The Shared Database:

All instances point to the same Job Repository (the BATCH_ tables). This allows the Manager to track which partitions succeeded and which need to be restarted.
## Why Spring Batch (not just a @Scheduled method)?

| Problem | @Scheduled alone | Spring Batch |
|---------|-----------------|--------------|
| Job crashed at record 500k — restart from scratch? | Yes | No — resumes from last checkpoint |
| How many records processed? | Log it yourself | Built-in JobRepository tracks everything |
| Skip bad records, retry transient failures | Code it yourself | Built-in skip/retry policies |
| Process in parallel partitions | Code it yourself | Built-in partitioning & multi-threading |
| Audit trail (start time, end time, exit status) | Code it yourself | Automatic in JobRepository |

## Core Concepts

```
Job
 └── Step 1 (chunk-oriented)
 │    ├── ItemReader      ← reads one item at a time
 │    ├── ItemProcessor   ← transforms / validates (optional)
 │    └── ItemWriter      ← writes a chunk (list) at a time
 └── Step 2 (tasklet)     ← arbitrary logic (e.g., move file, send email)
```

### Job
- Top-level unit. Has a name and one or more Steps.
- Launched by `JobLauncher` with `JobParameters` (used to identify a unique run).
- `JobParameters` make each execution unique: `date=2024-01-15`, `fileId=123`, etc.

### Step
- Single phase of a Job. Can be chunk-oriented or a Tasklet.
- **Tasklet** — simple: implement `execute()`, do whatever, return `RepeatStatus.FINISHED`.
- **Chunk-oriented** — the standard pattern for large data processing.

### Chunk-Oriented Processing
```
Read(1) → Process(1) → Read(1) → Process(1) → ... [chunk-size times] → Write(chunk)
```
- Items are read and processed ONE at a time.
- Writing happens in batches (chunks). If write fails, only that chunk rolls back — not the whole job.
- Chunk = unit of transaction. Checkpoint saved after each successful chunk.

```java
@Bean
public Step processRecordsStep(JobRepository jobRepository,
                                PlatformTransactionManager txManager) {
    return new StepBuilder("processRecordsStep", jobRepository)
        .<FinancialRecord, ProcessedRecord>chunk(500, txManager)  // chunk size = 500
        .reader(jdbcCursorReader())
        .processor(businessRuleProcessor())
        .writer(jdbcBatchWriter())
        .faultTolerant()
            .skipLimit(100)                          // skip up to 100 bad records
            .skip(ValidationException.class)
            .retryLimit(3)                           // retry transient errors 3x
            .retry(TransientDataAccessException.class)
        .build();
}
```

### JobRepository
- Persists all job/step execution metadata to a DB (`BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION`, `BATCH_STEP_EXECUTION` tables).
- Enables: restart from last checkpoint, execution history, monitoring.
- Spring Boot auto-configures it against your datasource.

## ItemReader Options

### JdbcCursorItemReader — best for large tables
```java
@Bean
public JdbcCursorItemReader<FinancialRecord> jdbcCursorReader(DataSource ds) {
    return new JdbcCursorItemReaderBuilder<FinancialRecord>()
        .name("financialRecordReader")
        .dataSource(ds)
        .sql("SELECT * FROM financial_records WHERE status = 'PENDING' ORDER BY id")
        .rowMapper(new BeanPropertyRowMapper<>(FinancialRecord.class))
        .fetchSize(500)          // JDBC fetch size — controls DB→app network batching
        .build();
}
```
- Keeps a single DB cursor open for the entire step — memory-efficient (streams rows).
- Not restartable by default (cursor position lost on crash). Use `JdbcPagingItemReader` for restartability.

### JdbcPagingItemReader — restartable
```java
@Bean
public JdbcPagingItemReader<FinancialRecord> pagingReader(DataSource ds) {
    Map<String, Order> sortKeys = Map.of("id", Order.ASCENDING);
    return new JdbcPagingItemReaderBuilder<FinancialRecord>()
        .name("pagingReader")
        .dataSource(ds)
        .selectClause("SELECT *")
        .fromClause("FROM financial_records")
        .whereClause("WHERE status = 'PENDING'")
        .sortKeys(sortKeys)
        .pageSize(500)
        .rowMapper(new BeanPropertyRowMapper<>(FinancialRecord.class))
        .build();
}
```
- Re-issues paginated queries using saved offset → survives restart.

### FlatFileItemReader — CSV/TSV files
```java
new FlatFileItemReaderBuilder<FinancialRecord>()
    .name("csvReader")
    .resource(new FileSystemResource("/data/records.csv"))
    .delimited().names("id", "amount", "currency")
    .targetType(FinancialRecord.class)
    .build();
```

## ItemProcessor

```java
@Component
public class BusinessRuleProcessor implements ItemProcessor<FinancialRecord, ProcessedRecord> {

    @Override
    public ProcessedRecord process(FinancialRecord item) throws Exception {
        if (item.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
            throw new ValidationException("Invalid amount: " + item.getId());
            // or return null to silently filter/skip the item
        }
        return new ProcessedRecord(item.getId(), applyBusinessRules(item));
    }
}
```
- Return `null` to filter an item (it won't be written).
- Throw an exception to trigger skip or retry logic.

## ItemWriter

### JdbcBatchItemWriter — efficient bulk insert
```java
@Bean
public JdbcBatchItemWriter<ProcessedRecord> jdbcBatchWriter(DataSource ds) {
    return new JdbcBatchItemWriterBuilder<ProcessedRecord>()
        .dataSource(ds)
        .sql("INSERT INTO processed_records (id, result, processed_at) VALUES (:id, :result, :processedAt)")
        .beanMapped()   // maps bean properties to named params
        .build();
}
```
Uses JDBC batch (`addBatch()` / `executeBatch()`) — one round trip per chunk.

## Restartability

- Job is restartable if `Job.preventRestart()` is NOT called.
- On restart: Spring Batch reads `BATCH_STEP_EXECUTION` to find last committed chunk → skips already-processed records.
- `JdbcPagingItemReader` supports this; `JdbcCursorItemReader` does not.
- `JobParameters` must be identical for a restart to continue the same `JobInstance`.

```java
// Force a new unique run each time (for scheduled jobs):
JobParameters params = new JobParametersBuilder()
    .addLocalDateTime("runAt", LocalDateTime.now())
    .toJobParameters();
jobLauncher.run(job, params);
```

## Parallel Processing

### Multi-threaded Step (same step, multiple threads)
```java
.taskExecutor(new SimpleAsyncTaskExecutor())
.throttleLimit(4)  // 4 threads
// WARNING: reader must be thread-safe — JdbcCursorItemReader is NOT
// Use JdbcPagingItemReader (synchronized) or SynchronizedItemStreamReader wrapper
```

### Partitioning (split data range across workers)
```java
// Partitioner splits id range into N partitions
public class RangePartitioner implements Partitioner {
    public Map<String, ExecutionContext> partition(int gridSize) {
        long range = totalCount / gridSize;
        // return map of "partition0" → {minId: 0, maxId: 1000000}, etc.
    }
}
// Each partition runs its own Step with its own reader/writer
```
Best for: truly independent data slices (e.g., by date range, by region, by id range).

## Skip vs Retry vs Fail

```java
.faultTolerant()
    // Skip: record is bad data, log it and continue
    .skipLimit(200)
    .skip(ValidationException.class)
    .skip(DataIntegrityViolationException.class)

    // Retry: transient failure (DB timeout, network blip), retry same record
    .retryLimit(3)
    .retry(TransientDataAccessException.class)

    // No skip/retry for these — fail the job immediately
    .noSkip(FatalBusinessException.class)
    .noRetry(NonTransientDataAccessException.class)
```

Track skipped items with `SkipListener`:
```java
public class AuditSkipListener implements SkipListener<FinancialRecord, ProcessedRecord> {
    public void onSkipInProcess(FinancialRecord item, Throwable t) {
        auditRepo.logSkipped(item.getId(), t.getMessage());
    }
}
```

## Full Example Skeleton

```java
@Configuration
@EnableBatchProcessing
public class FinancialBatchConfig {

    @Bean
    public Job processFinancialRecordsJob(JobRepository repo, Step step) {
        return new JobBuilder("processFinancialRecordsJob", repo)
            .start(step)
            .build();
    }

    @Bean
    public Step processStep(JobRepository repo, PlatformTransactionManager tx,
                            DataSource ds) {
        return new StepBuilder("processStep", repo)
            .<FinancialRecord, ProcessedRecord>chunk(500, tx)
            .reader(pagingReader(ds))
            .processor(new BusinessRuleProcessor())
            .writer(jdbcBatchWriter(ds))
            .faultTolerant()
                .skipLimit(100).skip(ValidationException.class)
                .retryLimit(3).retry(TransientDataAccessException.class)
            .build();
    }
}
```

## Interview Sound Bites

**"Why chunk size 500 and not 1 or 10000?"**
> Chunk is the transaction boundary. Too small → too many commits, overhead dominates. Too large → one failure rolls back and replays a huge batch, and memory pressure increases. 100–1000 is typical; tune based on row size and DB latency.

**"What happens if the job crashes halfway through?"**
> Spring Batch saves a checkpoint after every committed chunk in JobRepository. On restart, it picks up from the last committed chunk. For this to work the reader must be restartable (JdbcPagingItemReader, not cursor reader).

**"How would you process 10M records without running out of memory?"**
> JdbcCursorItemReader streams rows via a JDBC cursor — only one row in memory at a time (plus the current chunk buffer). Never load all records into a List. Combine with a chunk size of ~500 and flush/clear the EntityManager if using JPA.

**"How do you run this job nightly?"**
> Either `@Scheduled` + `JobLauncher` in the same app, or externally via a cron job / AWS EventBridge triggering an ECS task or Lambda. In enterprise environments I'd prefer the external trigger to keep the batch app stateless and independently deployable.
