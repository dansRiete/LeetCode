# 13.1 What is Spring Boot? How does auto-configuration work?

## Complete Answer

### Spring Boot vs Spring Framework
- **Spring Framework** — powerful but requires manual configuration (XML or Java config): beans, datasources, MVC setup, etc.
- **Spring Boot** — opinionated wrapper around Spring: auto-configures everything based on what's on the classpath. You focus on business logic, not wiring.

### Auto-configuration mechanism
Spring Boot scans `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
in each starter jar. If the required classes are on the classpath, it applies the configuration automatically.

Example: add `spring-boot-starter-data-jpa` to `pom.xml` →
Spring Boot auto-configures `DataSource`, `EntityManagerFactory`, `TransactionManager` for you.

```java
// Without Spring Boot — manual wiring
@Bean
public DataSource dataSource() { ... }

@Bean
public EntityManagerFactory entityManagerFactory() { ... }

// With Spring Boot — nothing needed, auto-configured from application.properties
spring.datasource.url=jdbc:postgresql://localhost/mydb
spring.datasource.username=user
spring.datasource.password=secret
```

### @SpringBootApplication
Three annotations in one:
```java
@SpringBootApplication
// = @Configuration + @EnableAutoConfiguration + @ComponentScan
```
- `@Configuration` — this class defines beans
- `@EnableAutoConfiguration` — trigger auto-config
- `@ComponentScan` — scan current package and subpackages for `@Component`, `@Service`, `@Repository`, `@Controller`

### Key stereotypes
| Annotation | Use for |
|---|---|
| `@Component` | Generic Spring-managed bean |
| `@Service` | Business logic layer |
| `@Repository` | Data access layer (also translates DB exceptions) |
| `@Controller` / `@RestController` | HTTP layer |

### Starters — curated dependency bundles
- `spring-boot-starter-web` — Tomcat + Spring MVC + Jackson
- `spring-boot-starter-data-jpa` — Hibernate + datasource
- `spring-boot-starter-security` — Spring Security
- `spring-boot-starter-actuator` — health/metrics endpoints
- `spring-boot-starter-test` — JUnit 5 + Mockito + AssertJ

### Actuator — important for integration engineers
Exposes operational endpoints out of the box:
```
GET /actuator/health   → service health
GET /actuator/metrics  → JVM, HTTP, custom metrics
GET /actuator/env      → current config properties
```

### Spring profiles
```properties
# application-dev.properties / application-prod.properties
spring.profiles.active=prod
```
Activate with env var: `SPRING_PROFILES_ACTIVE=prod`

### Interview answer structure
> "Spring Boot eliminates boilerplate Spring configuration through auto-configuration —
> it detects what's on the classpath and wires sensible defaults automatically.
> @SpringBootApplication combines component scanning, configuration, and auto-config
> in one annotation. You override defaults via application.properties.
> Starters are curated dependency sets that trigger the relevant auto-configuration."

## Questions & Answers

### What is the difference between @Component and @Service in Spring?

Technically, `@Service` is just `@Component` with a different name — Spring treats them identically during component scanning. Both register the class as a Spring bean. The difference is **semantic and tooling-related**:

- `@Component` — generic stereotype, use when no more specific annotation fits.
- `@Service` — signals business-logic layer intent; makes architecture explicit and aids tools like Spring AOP (you can point-cut `@Service` classes specifically) and static analysis.

```java
// These two are functionally equivalent in terms of bean registration:

@Component
public class EmailSender { ... }       // works, but intent unclear

@Service
public class EmailSender { ... }       // preferred — signals service layer
```

Under the hood, `@Service` is defined as:
```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component          // <-- it IS a @Component
public @interface Service { ... }
```

**Key points:**
- Both are picked up by `@ComponentScan` identically
- `@Service` carries no extra behaviour — it's a marker annotation
- `@Repository` adds value beyond marking: it wraps persistence exceptions into Spring's `DataAccessException` hierarchy
- Use the most specific stereotype available: `@Service` for business logic, `@Repository` for DAOs, `@Controller`/`@RestController` for HTTP layer, `@Component` only for utilities that don't fit elsewhere

**Common mistakes:**
- Thinking `@Service` adds transactional behaviour — it does NOT; you still need `@Transactional`
- Using `@Component` everywhere "to be safe" — wastes the semantic signal that stereotypes provide
- Confusing `@Repository`'s exception translation (real behaviour) with `@Service`'s purely semantic role
