## Complete Answer

### CompletableFuture vs Future:
- Future: blocking only (get()), no chaining, no callbacks, no exception handling
- CompletableFuture: non-blocking callbacks, chainable, composable, manually completable

### thenApply vs thenCompose vs thenCombine:
- `thenApply` — sync transform, like map(): `order -> order.getId()`
- `thenCompose` — async chain, like flatMap(): next step also returns CF
- `thenCombine` — zip two independent futures: `(order, customer) -> ...`

### Fan-out pattern:
```java
List<CompletableFuture<Order>> futures = partnerIds.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> fetchOrder(id), executor))
    .toList();

List<Order> results = CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
    .thenApply(v -> futures.stream().map(CompletableFuture::join).toList())
    .get(10, TimeUnit.SECONDS);
```
- allOf() takes array not list
- join() is unchecked, cleaner inside streams
- Always use custom executor for I/O, not ForkJoinPool.commonPool()

### Exception handling:
| Method | Called when | Changes result | Use for |
|--------|------------|----------------|---------|
| exceptionally | Exception only | Yes (fallback) | Default value on failure |
| handle | Always | Yes | Transform both success and error |
| whenComplete | Always | No | Logging, metrics side effects |

```java
// Fallback to cache on partner failure
CompletableFuture.supplyAsync(() -> partnerApi.getPrice(id))
    .exceptionally(ex -> cachedPrice(id))
    .thenAccept(price -> displayPrice(price));
```

## Questions & Answers

### What is the primary difference between thenApply() and thenAccept() in a CompletableFuture chain?

**`thenApply()`**:
- Takes a `Function<T, R>` (an input, and returns an output).
- Is used to **transform** the result of the previous step.
- Returns a new `CompletableFuture<R>` containing the transformed value.

**`thenAccept()`**:
- Takes a `Consumer<T>` (takes an input, but returns `void`).
- Is used to **consume** the result, usually at the end of the chain (side-effects like saving to DB or printing).
- Returns a `CompletableFuture<Void>`.

**Key points:**
- `thenApply` = Transform (returns something)
- `thenAccept` = Consume (returns nothing/void)

---

### What is the difference between thenApply() and thenCompose()?

**`thenApply()`**:
- Used for synchronous transformations.
- Equivalent to `map()` in Streams.
- The lambda returns a normal object (e.g., `String`, `User`).

**`thenCompose()`**:
- Used for chaining asynchronous operations.
- Equivalent to `flatMap()` in Streams.
- The lambda returns another `CompletableFuture`. If you used `thenApply()` instead, you would get a nested `CompletableFuture<CompletableFuture<T>>`!

### Imagine you are building a high-throughput microservice that uses CompletableFuture to make parallel downstream API calls. If you use the default ForkJoinPool, what issues might you encounter under heavy load, and how would you fix it?

By default, `CompletableFuture.supplyAsync()` uses `ForkJoinPool.commonPool()`. This pool is sized based on the number of CPU cores (e.g., `availableProcessors() - 1`).

If your application does blocking I/O (like calling downstream HTTP APIs or querying a database), those few threads will quickly block waiting for network responses.

**The Issue: Thread Starvation**
Once all threads in the common pool are blocked, the entire application grinds to a halt. Any other components relying on parallel streams or the common pool will also be blocked.

**The Fix:**
You must provide a dedicated, correctly sized custom thread pool (like a `ThreadPoolExecutor`) specifically for I/O operations.

```java
ExecutorService ioExecutor = Executors.newFixedThreadPool(100);
CompletableFuture.supplyAsync(() -> apiCall(), ioExecutor);
```
