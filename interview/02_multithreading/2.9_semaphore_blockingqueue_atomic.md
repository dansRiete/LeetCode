## Complete Answer

### CountDownLatch:
```java
CountDownLatch latch = new CountDownLatch(3);
executor.submit(() -> { doWork(); latch.countDown(); });
latch.await(5, TimeUnit.SECONDS); // block until count = 0
```
One-time use. Use for: fan-out wait, async test synchronization, startup gates.

### Semaphore — N threads allowed simultaneously:
```java
Semaphore semaphore = new Semaphore(3); // max 3 concurrent
semaphore.acquire();
try { partnerApi.call(); } finally { semaphore.release(); }
```
vs synchronized/ReentrantLock = 1 thread at a time.
Use for: rate limiting, throttling concurrent partner calls.

### BlockingQueue — thread-safe producer/consumer:
```java
BlockingQueue<Order> queue = new ArrayBlockingQueue<>(500);
queue.put(order);  // blocks if full — natural backpressure
queue.take();      // blocks if empty
```
Implementations: LinkedBlockingQueue, ArrayBlockingQueue, PriorityBlockingQueue, SynchronousQueue.
Used internally by ThreadPoolExecutor for pending tasks.

### AtomicInteger / CAS:
```java
// CAS — single CPU instruction (CMPXCHG), no kernel involvement
if (current == expected) { current = newValue; return true; }

AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet(); // thread-safe, no synchronized
```
- Low contention → faster than synchronized (no thread parking)
- High contention → spin loop burns CPU → synchronized wins
- Rule: single variable → Atomic*, multiple variables together → lock

## Questions & Answers

### In a high-throughput service, how would you choose between an AtomicInteger and a synchronized counter?

**Your Answer (session):**
- synchronized for high contention environments to avoid lots of retries and atomicint for less contention and less blocking

**Complete Answer:**
You accurately identified the core tradeoff:
- **`AtomicInteger` (CAS):** In low/medium contention, it is insanely fast because it uses a single CPU instruction and doesn't force the OS to pause/resume the thread (no context switching). But in **extreme contention**, threads enter a "spin loop" (constantly retrying the CAS), which burns 100% of a CPU core doing nothing.
- **`synchronized` (Locks):** Forces the OS to suspend the thread and put it in a queue. Suspending/resuming a thread is expensive, but it prevents the thread from burning CPU while it waits. 

**The Modern Senior Answer (`LongAdder`):**
In Java 8+, if you actually have extreme contention on a counter, you shouldn't use *either* of those! You should use **`LongAdder`**. It creates an array of counters behind the scenes, letting different threads increment their own dedicated cell without colliding. When you call `.sum()`, it adds them all up.
