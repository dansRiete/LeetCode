# 2.8 What is a deadlock? Describe the four conditions required and one prevention strategy.

## Your Answer
- Thread A waits for lock held by Thread B, Thread B waits for lock held by Thread A ✓
- One condition: "at least two threads" ✗ (not a Coffman condition)

## What Was Missing / Wrong
- Missing: the four **Coffman conditions** by name
- Missing: concrete prevention strategy (lock ordering, tryLock with timeout, etc.)

## Complete Answer

### Definition:
A deadlock occurs when two or more threads are permanently blocked, each waiting
for a resource held by another.

### Four Coffman Conditions (ALL must hold):
1. **Mutual exclusion** — resource held by only one thread at a time
2. **Hold and wait** — thread holds a resource while waiting to acquire another
3. **No preemption** — resources cannot be forcibly taken; only voluntarily released
4. **Circular wait** — T1 waits for T2, T2 waits for T1 (the cycle)

Break any one → deadlock impossible.

### Prevention strategies:

**1. Consistent lock ordering** (breaks circular wait):
```java
void transfer(Account from, Account to) {
    Account first  = from.id < to.id ? from : to;
    Account second = from.id < to.id ? to : from;
    synchronized (first) {
        synchronized (second) { ... }
    }
}
```

**2. tryLock with timeout** (breaks hold-and-wait indefinitely):
```java
if (lock1.tryLock(100, MILLISECONDS)) {
    try {
        if (lock2.tryLock(100, MILLISECONDS)) {
            try { ... } finally { lock2.unlock(); }
        }
    } finally { lock1.unlock(); }
}
```

**3. Avoid nested locks** — acquire only one lock at a time when possible.

## Q: Does deadlock only happen if threads start simultaneously?

No — it's a **race condition**, not a guaranteed outcome. It depends on interleaving:

```
Thread 1: acquires lockA...
Thread 2: acquires lockB...        ← both hold one lock
Thread 1: tries to acquire lockB  ← blocked
Thread 2: tries to acquire lockA  ← blocked → deadlock
```

If Thread 1 runs fast enough to grab both locks first, no deadlock that time.

**Why this is dangerous:**
- Works fine in testing (low load, no interleaving)
- Deadlocks in production under high concurrency
- Once deadlocked — threads hang **forever**, no timeout, no exception, no log

Consistent lock ordering makes deadlock **structurally impossible** regardless of timing.

## Classic deadlock code example:

```java
Object lockA = new Object();
Object lockB = new Object();

// Thread 1: acquires A then B
synchronized (lockA) {
    synchronized (lockB) { doWork(); }
}

// Thread 2: acquires B then A — opposite order = deadlock possible
synchronized (lockB) {
    synchronized (lockA) { doWork(); }
}

// Fix: both threads acquire in same order A → B
synchronized (lockA) {
    synchronized (lockB) { doWork(); }
}
```

## Questions & Answers

### Imagine we have a high-throughput module in Ignition that suddenly starts hanging and throughput drops to zero. You suspect a deadlock or thread starvation. Walk me through exactly how you would use JVM tools in production to generate thread dumps and what specific thread states or patterns you would look for in those dumps to confirm your diagnosis.

**Ideal Answer:**
First, I would capture the thread dump using a JVM tool like `jstack <pid>` or `jcmd <pid> Thread.print` (preferring `jcmd` on modern JVMs). If the system is under high CPU load, I would correlate it by using `top -H -p <pid>` to get the native thread IDs, convert them to hex, and find the corresponding NID in the thread dump.

To confirm the diagnosis:
1. **Deadlock**: I would scroll to the bottom of the `jstack` output. The JVM automatically detects monitor and lock deadlocks and will explicitly print "Found one Java-level deadlock:" listing the threads and the specific locks forming the circular dependency. I would look for threads in the `BLOCKED (on object monitor)` state waiting on each other.
2. **Thread Starvation**: If it's starvation (like a connection pool exhaustion or a blocked I/O thread), I would see many worker threads in `WAITING` or `TIMED_WAITING` state (e.g., parked on `LockSupport` or waiting on a connection pool lock), with the active threads either blocked on a slow external resource or stuck in an infinite loop (`RUNNABLE` state).

**Key points:**
* Mention specific tools: `jstack`, `jcmd`, or APMs
* Mention JVM's automatic deadlock detection at the end of the thread dump
* Identify the `BLOCKED` state for deadlocks vs `WAITING` / `TIMED_WAITING` for starvation
* Mention correlating high CPU threads using `top -H` to `nid` in thread dumps

**Common mistakes:**
* Saying they would just look at logs (thread dumps are required for deadlocks)
* Confusing `BLOCKED` (waiting for a lock) with `WAITING` (waiting for a condition/pool)
* Not knowing the JVM prints explicit deadlock warnings in the dump
