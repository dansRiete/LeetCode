# ConcurrentHashMap — Deep Dive

---

## Q: What are all the thread-safe Map options in Java?

| | Thread-safe | Lock scope | Notes |
|---|---|---|---|
| `HashMap` | No | — | Single-threaded only |
| `Hashtable` | Yes | Whole map | Legacy, avoid in new code |
| `Collections.synchronizedMap(map)` | Yes | Whole map | Wraps any map, same as Hashtable effectively |
| `ConcurrentHashMap` | Yes | Bucket-level | Best for general concurrent use |
| `ConcurrentSkipListMap` | Yes | Fine-grained | Sorted map — use when you need concurrent `TreeMap` |

- `Hashtable` and `synchronizedMap` → one thread at a time, anywhere in the map
- `ConcurrentHashMap` → many threads simultaneously, just not in the same bucket
- `ConcurrentSkipListMap` — often forgotten; use when you need sorted keys concurrently

**Rule:** `ConcurrentHashMap` for general use, `ConcurrentSkipListMap` for sorted keys. Forget `Hashtable` exists.

## Q: What is the difference between HashMap and ConcurrentHashMap?

### Your Answer (session)
- ConcurrentHashMap is thread-safe ✓
- Uses CAS under the hood ✓

### What Was Missing
- CAS is only for empty-bucket inserts — also uses **synchronized on individual buckets** for collision chains
- Key distinction: `Hashtable` / `Collections.synchronizedMap()` lock the **entire map**; ConcurrentHashMap locks only the **affected bucket** → much better throughput
- **Compound operations are not atomic** — individual `get()` and `put()` are safe, but `get()` + `put()` together are not
- Use `putIfAbsent()`, `computeIfAbsent()`, `compute()`, `merge()` for atomic compound operations
- ConcurrentHashMap does **not** allow null keys or values; HashMap does

### Complete Answer

| | HashMap | ConcurrentHashMap |
|---|---|---|
| Thread safe | No | Yes |
| Locking | None | Bucket-level |
| Null keys | Yes | No |
| Performance | Faster (single thread) | Slower but concurrent |

**How thread safety is achieved:**
- **CAS** — inserting into an empty bucket (lock-free)
- **synchronized on bucket** — chaining within a non-empty bucket
- Result: threads on different buckets run fully in parallel; reads (`get`) are always lock-free

```java
// NOT thread safe even with ConcurrentHashMap
String val = map.get("key");
if (val == null) {
    map.put("key", "value"); // race condition
}

// thread safe — atomic
map.computeIfAbsent("key", k -> "value");
map.putIfAbsent("key", "value");
```

## Q: What is CAS — how does it work mechanically?

### Your Answer (session)
- Compare And Swap ✓
- Checks value then swaps if true ✓
- Uses CPU-optimized instruction ✓

### What Was Missing
- Three-argument structure: `CAS(memoryLocation, expectedValue, newValue)`
- If current == expected → atomically swap, return true
- If not → do nothing, return false → caller retries in a loop
- In Java: `AtomicInteger`, `AtomicReference` use `Unsafe.compareAndSwapInt()` under the hood
- Lock-free but NOT wait-free — threads may spin

## Q: What is the ABA problem, and how does Java solve it?

### Your Answer (session)
- Not sure ✗

### Complete Answer

Thread 1 reads value `A`.
Thread 2 changes: `A → B → A`.
Thread 1 does CAS: sees `A`, assumes nothing changed → succeeds — but the value **was** modified in between.

Usually harmless for counters, but dangerous with pointers/references (e.g. lock-free linked lists — a node can be removed and re-added, causing Thread 1 to miss the structural change).

**Java fix: `AtomicStampedReference`**

```java
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
// requires both value AND stamp (version counter) to match
ref.compareAndSet("A", "B", 0, 1); // old value, new value, old stamp, new stamp
```

Every update increments the stamp: `A(0) → B(1) → A(2)` — Thread 1's CAS fails because stamp 0 ≠ 2.

Rarely comes up in application code; matters in lock-free data structure internals.

## Q: ConcurrentHashMap uses synchronized on buckets — doesn't that block threads? How is it still "high concurrency"?

### Your Answer (session)
- "It uses CAS so it shouldn't block" (partially deflected) ✗

### Complete Answer

Yes, synchronized does block — but only for that **specific bucket**.

Two reasons it's still high concurrency:
1. **Lock granularity** — the map has 16+ buckets by default. Threads on different buckets run fully in parallel. `synchronizedMap` would block all of them on a single lock.
2. **Reads are never locked** — `get()` is completely lock-free. In read-heavy workloads, there's almost no contention.

With a good hash function and a properly-sized map, the probability of two threads colliding on the exact same bucket is low.

## Q: Is `size()` reliable on ConcurrentHashMap?

### Your Answer (session)
- Not sure ✗

### Complete Answer

No. `size()` returns a **snapshot estimate**. Between counting and acting on the result, other threads may insert or remove entries.

Computing an exact size would require locking the entire map — defeating the purpose.

**Rule:** never make decisions based on `ConcurrentHashMap.size()` in concurrent code. Use `isEmpty()` as a rough signal at best, or redesign to not need the size.

## Q: What can actually go wrong if two threads write to a plain HashMap simultaneously?

### Your Answer (session)
- They can try to update the same bucket ✓ (partial)

### Complete Answer

**1. Lost updates** — two threads insert into the same bucket, one silently overwrites the other.

**2. Corrupted size counter** — `size` is not atomic; can drift incorrect.

**3. The Java 7 infinite loop (famous production bug):**

During concurrent rehash in Java 7, the linked list in a bucket can become circular:

```
Thread 1: A → B → null  (rehashing)
Thread 2: B → A → null  (rehashing concurrently)
Result:   A → B → A → B → ...  ← infinite loop
```

Any subsequent `get()` on that key loops forever, pegging a CPU core at 100% with no crash or error.

**Java 8 fixed this** (changed rehash order), but the map is still not thread-safe — lost updates and corrupt state remain possible.

## Q: When would you choose `Collections.synchronizedMap` over ConcurrentHashMap?

### Your Answer (session)
- Not sure ✗

### Complete Answer

Almost never. The one theoretical case:

```java
Map<String, String> map = Collections.synchronizedMap(new HashMap<>());

synchronized (map) {
    if (!map.containsKey("key")) {
        map.put("key", "value");  // check-then-put is atomic
    }
}
```

With `ConcurrentHashMap` there's no single lock to grab, so you must use `computeIfAbsent()` instead.

**In practice:** `computeIfAbsent()` is cleaner and faster. `synchronizedMap` has worse throughput and is easy to misuse (forgetting the `synchronized` block gives false safety). Always prefer `ConcurrentHashMap` with atomic compound methods in new code.

## Q: You have a Collections.synchronizedMap() and a ConcurrentHashMap(). If multiple threads are reading and writing to them simultaneously, what happens if you try to iterate over the keys of both maps? Do you need to do anything special?

### Your Answer (session)
- Collections.synchronizedMap() will throw an Exception ✓ (partial)
- ConcurrentHashMap() allows parallel updates but iteration is not 100% guaranteed ✓

### What Was Missing
- Which exact exception: `ConcurrentModificationException`
- **Crucial:** You must manually wrap `Collections.synchronizedMap()` in a `synchronized(map)` block during iteration, otherwise it is unsafe.
- Formal terminology: `ConcurrentHashMap` uses a **weakly-consistent iterator**. "Not 100% guaranteed" means it is guaranteed not to throw an exception, but may not show updates made after the iterator was constructed.

### Complete Answer

**Collections.synchronizedMap()**:
- Its iterator is **fail-fast**.
- If modified concurrently, it throws `ConcurrentModificationException`.
- **Special action required:** You must manually synchronize on the map object during the entire iteration.
```java
synchronized (syncMap) {
    for (Object key : syncMap.keySet()) { ... }
}
```

**ConcurrentHashMap()**:
- Its iterator is **weakly-consistent**.
- It will never throw a `ConcurrentModificationException`.
- **No special action required:** You can iterate safely without external synchronization.
- It iterates over the map as it existed upon construction and may or may not reflect subsequent modifications.
