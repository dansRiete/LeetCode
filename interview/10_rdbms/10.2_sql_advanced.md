## Window Functions

Window functions compute a value for each row based on a "window" of related rows — without collapsing rows like GROUP BY does.

```sql
-- Running total per user
SELECT user_id, order_date, amount,
       SUM(amount) OVER (PARTITION BY user_id ORDER BY order_date) AS running_total
FROM orders;

-- Rank employees by salary within department
SELECT dept, name, salary,
       RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
FROM employees;

-- Previous row value (LAG)
SELECT user_id, order_date, amount,
       LAG(amount) OVER (PARTITION BY user_id ORDER BY order_date) AS prev_amount
FROM orders;
```

Key functions: `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `LAG()`, `LEAD()`, `FIRST_VALUE()`, `LAST_VALUE()`, `SUM/AVG/COUNT OVER()`

## JOINs

| Type | Returns |
|------|---------|
| `INNER JOIN` | Only rows with matches on both sides |
| `LEFT JOIN` | All left rows + matched right rows (NULL if no match) |
| `RIGHT JOIN` | All right rows + matched left rows |
| `FULL OUTER JOIN` | All rows from both sides (NULLs where no match) |
| `CROSS JOIN` | Cartesian product (every combination) |
| `SELF JOIN` | Table joined with itself (e.g., employee → manager) |

**Common trap:** filtering on a LEFT JOIN in WHERE converts it to INNER JOIN:
```sql
-- This is actually an INNER JOIN despite LEFT JOIN:
SELECT * FROM orders o LEFT JOIN customers c ON o.cid = c.id
WHERE c.country = 'US';  -- filters out NULLs → loses unmatched orders

-- Correct: filter in ON clause
SELECT * FROM orders o LEFT JOIN customers c ON o.cid = c.id AND c.country = 'US';
```

## Indexes

### B-Tree (default)
- Balanced tree; supports `=`, `<`, `>`, `BETWEEN`, `LIKE 'prefix%'`
- Most common; used for primary keys and foreign keys
- O(log n) lookup

### Hash Index
- Only supports `=` lookups, faster than B-tree for equality
- Not WAL-logged in older Postgres (not crash-safe pre-10); rarely preferred

### GIN (Generalized Inverted Index)
- Used for full-text search, JSONB keys, arrays
- `WHERE tags @> ARRAY['java']` or `WHERE doc @@ to_tsquery('java')`

### GiST
- Used for geometric/range types, full-text search variants
- More flexible than GIN, slower updates

### Partial Index
```sql
-- Index only active users — smaller, faster for filtered queries
CREATE INDEX idx_active_users ON users(email) WHERE status = 'ACTIVE';
```

### Expression Index
```sql
-- Index lower(email) to support case-insensitive search
CREATE INDEX idx_email_lower ON users(lower(email));
```

### Covering Index (INCLUDE)
```sql
-- Include salary so query can be answered from index alone (index-only scan)
CREATE INDEX idx_emp_dept ON employees(dept_id) INCLUDE (salary);
```

## ACID

| Property | Meaning |
|----------|---------|
| **Atomicity** | All-or-nothing: either all statements in a transaction commit or all roll back |
| **Consistency** | DB moves from one valid state to another; constraints are never violated |
| **Isolation** | Concurrent transactions don't see each other's intermediate state |
| **Durability** | Committed data survives crashes (written to WAL / disk) |

## Transaction Isolation Levels & Anomalies

| Level | Dirty Read | Non-repeatable Read | Phantom Read |
|-------|-----------|---------------------|--------------|
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | prevented | possible | possible |
| REPEATABLE READ | prevented | prevented | possible (prevented in PG) |
| SERIALIZABLE | prevented | prevented | prevented |

- **Dirty read**: reading uncommitted data from another transaction
- **Non-repeatable read**: same row read twice yields different values (other tx committed between reads)
- **Phantom read**: same range query yields different rows (other tx inserted between reads)

PostgreSQL default: `READ COMMITTED`. For financial ledgers or batch jobs that must see a consistent snapshot: `REPEATABLE READ` or `SERIALIZABLE`.

## Optimistic vs Pessimistic Locking

**Pessimistic** — lock the row when you read it; no one else can modify until you commit.
```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- other sessions block here until this transaction commits
```
Use when: high contention, short transactions, data must not change mid-process.

**Optimistic** — read without lock; check version at write time; retry if someone changed it.
```sql
-- Read
SELECT id, balance, version FROM accounts WHERE id = 1;
-- Write — only updates if version hasn't changed
UPDATE accounts SET balance = 950, version = version + 1
WHERE id = 1 AND version = 5;
-- If 0 rows affected → someone else updated → retry
```
Use when: low contention, long-lived business transactions, microservices. JPA `@Version` implements this pattern.

## Query Optimization Checklist

1. **EXPLAIN ANALYZE** — see actual row counts vs estimates, find seq scans
2. **Check indexes** — missing index on WHERE/JOIN columns? Column order in composite index?
3. **Avoid functions on indexed columns** — `WHERE UPPER(email) = 'X'` kills index; use expression index instead
4. **SELECT only needed columns** — avoid `SELECT *`; enables index-only scans
5. **Avoid N+1** — use JOINs or batch fetching instead of looping queries in app code
6. **Update statistics** — `ANALYZE table` to refresh planner stats
7. **Pagination** — prefer keyset/cursor pagination over `OFFSET` on large tables
8. **Partitioning** — for very large tables, partition by date/range to enable partition pruning

```sql
EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id)
FROM users u JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2024-01-01'
GROUP BY u.name;
-- Look for: "Seq Scan" on large tables, high "rows" estimates vs actuals, nested loops on large sets
```

## CTE vs Subquery vs Temp Table

| | CTE (`WITH`) | Subquery | Temp Table |
|---|---|---|---|
| Readability | High (named, reusable in query) | Lower for complex | Clear |
| Materialized | Depends on DB/version | Inlined by optimizer | Always materialized |
| Reuse in same query | Yes | No (repeat inline) | Yes (separate query) |
| Indexes | No | No | Yes |
| Session scope | Query only | Query only | Session / transaction |
| Best for | Readable multi-step logic, recursive queries | Simple one-off filters | Large intermediate results needing index |

```sql
-- Recursive CTE — org hierarchy
WITH RECURSIVE org AS (
  SELECT id, name, manager_id FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id FROM employees e JOIN org ON e.manager_id = org.id
)
SELECT * FROM org;
```

## Reducing DB Load During Batch Jobs

The problem: a nightly batch job competes with live user traffic on the same DB.

**Read side:**
- **Read replica** — point the batch `ItemReader` at a replica datasource. Primary is untouched by SELECTs.

**Write side:**
- **JDBC batching** — `JdbcBatchItemWriter` groups chunk writes into one `executeBatch()` call. 500 records = 1 round trip instead of 500. Most impactful write-side optimization.
- **Off-peak scheduling** — run at 2–4am. Simple but effective.
- **Throttle the job** — limit thread count (`throttleLimit`) or add inter-chunk delay. Trade job duration for DB headroom.
- **Staging table swap** — write to `processed_records_staging` (no indexes, no FK constraints → fast). When complete, swap with real table via rename or bulk `INSERT INTO real SELECT * FROM staging`. Indexes live only on the final table.
- **Separate connection pool** — batch job uses its own low-priority pool so it cannot starve the API's connections.

**Interview answer (combine these):**
> "On the read side I'd point the batch reader at a read replica. On the write side, JDBC batching in JdbcBatchItemWriter reduces round trips to one per chunk. I'd schedule the job off-peak and throttle parallelism if the primary still shows contention. For very large one-off loads I'd write to a staging table with no indexes and swap it in once complete."

## Composite Index Column Ordering

**Rule: equality filters first → range filters → ORDER BY / GROUP BY → INCLUDE remaining SELECT columns**

```sql
-- Query: WHERE user_id = ? AND status = ? ORDER BY created_at DESC
CREATE INDEX idx ON transactions(user_id, status, created_at DESC);
-- user_id: equality → first
-- status:  equality → second
-- created_at: ORDER BY → last (already sorted in index, no filesort)

-- Query: WHERE created_at >= ? AND created_at < ? GROUP BY user_id  +  SUM(amount)
CREATE INDEX idx ON orders(created_at, user_id) INCLUDE (amount);
-- created_at: range → first (no equality, so range goes first)
-- user_id: GROUP BY → second
-- amount: INCLUDE for index-only scan (never touches table)
```

**How to spot a bad index with EXPLAIN ANALYZE:**
- `Seq Scan` on a large table → no index used
- `Filter:` instead of `Index Cond:` → condition applied row-by-row, not via index
- `rows removed by filter: 18000000` → scanned almost everything
- After fix: `Index Scan` with `Index Cond:` and no Filter line

## Lost Update & Concurrent Write Problems

**The problem:** two transactions read the same row, compute independently, both write back — the second write silently overwrites the first.

**Fix 1 — Pessimistic locking** (`SELECT FOR UPDATE`): lock at read time, second transaction waits.
```sql
SELECT * FROM accounts WHERE id = ? FOR UPDATE;
```
```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Account> findById(Long id);
```
Use when: high contention, financial operations, second transaction must *wait and succeed*.

**Fix 2 — Optimistic locking** (`@Version`): no lock; detect conflict at write time, caller retries.
```java
@Version int version;  // Hibernate adds WHERE version = ? to UPDATE
```
Use when: low contention, conflicts are rare, retry on failure is acceptable.

**Deadlock prevention:**
Two transactions locking the same two rows in opposite order → deadlock.
Fix: always acquire locks in a consistent order (e.g., lower ID first):
```java
long firstId  = Math.min(fromId, toId);
long secondId = Math.max(fromId, toId);
// lock firstId, then secondId — always
```
Safety net: set a lock timeout so deadlocks surface as errors rather than hanging forever.

## Functions on Indexed Columns

Wrapping an indexed column in a function defeats the index — the DB must evaluate the function on every row.

```sql
-- BAD — index on created_at unused:
WHERE YEAR(created_at) = 2024
WHERE DATE(created_at) = '2024-01-01'
WHERE UPPER(email) = 'FOO@BAR.COM'

-- GOOD — index usable:
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
WHERE email = 'foo@bar.com'  -- store emails lowercased, or use expression index
```

Expression index workaround if you can't change the query:
```sql
CREATE INDEX idx_email_lower ON users(lower(email));
-- Now WHERE lower(email) = 'foo@bar.com' uses the index
```

## N+1 Problem & Fix with JOIN

**Problem:** loading a collection with a loop fires one query per parent row.
```java
List<User> users = userRepo.findAll();          // 1 query
for (User u : users) {
    orderRepo.findByUserId(u.getId());           // 1 query × 1000 users = 1001 total
}
```

**Fix at SQL level — JOIN:**
```sql
SELECT u.id, u.name, o.id AS order_id, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
-- 1 query, all data
```

**Fix in Spring Data JPA — JOIN FETCH:**
```java
@Query("SELECT u FROM User u LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();
```

**Gotcha — JOIN FETCH + pagination:**
Hibernate cannot apply SQL `LIMIT` when fetching collections via JOIN FETCH — loads everything into memory first.
Fix: use `@BatchSize(size = 50)` on the collection instead, or fetch IDs first then load with JOIN FETCH.

## Aggregation: WHERE vs HAVING

**Clause order:** `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`

- `WHERE` — filters rows *before* grouping. Can use indexes. Always prefer here.
- `HAVING` — filters groups *after* aggregation. Use only for conditions on aggregated values.

```sql
-- Users with more than 3 orders in Jan 2024 and their total spend
SELECT u.id, u.name, SUM(o.amount) AS total_spend
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at >= '2024-01-01' AND o.created_at < '2024-02-01'  -- filter before group
GROUP BY u.id, u.name
HAVING COUNT(*) > 3                                                   -- filter after group
ORDER BY total_spend DESC;
```

## Finding and Deleting Duplicates

```sql
-- Find duplicate emails
SELECT email, COUNT(*) AS cnt
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;

-- Delete duplicates, keep lowest id per email
DELETE FROM customers
WHERE id NOT IN (
    SELECT MIN(id) FROM customers GROUP BY email
);

-- Alternative: ROW_NUMBER() — easier to change "keep" logic
DELETE FROM customers
WHERE id IN (
    SELECT id FROM (
        SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
        FROM customers
    ) t
    WHERE rn > 1
);
```

**Gotcha with `NOT IN`:** if subquery returns any `NULL`, entire `NOT IN` is false → nothing deleted. Safe when column is a non-null primary key.

## Data Integrity — Constraints

**CHECK constraint** (portable, easy to modify):
```sql
ALTER TABLE orders
ADD CONSTRAINT chk_order_status
CHECK (status IN ('PENDING', 'PROCESSING', 'COMPLETED', 'CANCELLED'));
```

**DB enum type** (PostgreSQL, self-documenting):
```sql
CREATE TYPE order_status AS ENUM ('PENDING', 'PROCESSING', 'COMPLETED', 'CANCELLED');
-- Adding a new value: ALTER TYPE order_status ADD VALUE 'REFUNDED';
```

**In JPA:** always use `EnumType.STRING`, never `ORDINAL` (ordinal breaks if enum order changes):
```java
@Enumerated(EnumType.STRING)
private OrderStatus status;
```

## Transaction Isolation Levels — Full Breakdown

### The three concurrency anomalies

**1. Dirty read** — reading uncommitted data from another transaction that may roll back:
```
T1: UPDATE accounts SET balance = 0   -- not committed
T2: SELECT balance → reads 0          -- dirty read
T1: ROLLBACK                          -- 0 was never real, T2 acted on ghost data
```

**2. Non-repeatable read** — same row read twice in one transaction returns different values:
```
T1: SELECT balance → 100
T2: UPDATE balance = 50; COMMIT
T1: SELECT balance → 50              -- changed mid-transaction
```

**3. Phantom read** — same range query returns different rows because another transaction inserted/deleted:
```
T1: SELECT COUNT(*) WHERE status='PENDING' → 10
T2: INSERT new PENDING order; COMMIT
T1: SELECT COUNT(*) WHERE status='PENDING' → 11   -- phantom row appeared
```

### What each level prevents

| Level | Dirty Read | Non-repeatable Read | Phantom Read |
|-------|-----------|---------------------|--------------|
| `READ UNCOMMITTED` | ❌ | ❌ | ❌ |
| `READ COMMITTED` | ✅ | ❌ | ❌ |
| `REPEATABLE READ` | ✅ | ✅ | ❌ (✅ in PostgreSQL) |
| `SERIALIZABLE` | ✅ | ✅ | ✅ |

PostgreSQL `REPEATABLE READ` also prevents phantoms — stricter than the SQL standard requires.

### Practical scenarios

**READ COMMITTED** — default, right for most API endpoints:
```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public UserDto getUser(long id) { ... }   // just need latest committed value
```

**REPEATABLE READ** — long reports, multi-table consistency:
```java
// Report reads claims, payments, adjustments over 3 minutes
// All must reflect the same point in time
@Transactional(isolation = Isolation.REPEATABLE_READ)
public ClaimsReport generate() { ... }
```

**SERIALIZABLE** — when a read drives a write decision (check-then-act):
```java
// "If no active subscription exists, create one"
// Without SERIALIZABLE: two threads both see none → both insert → duplicate
@Transactional(isolation = Isolation.SERIALIZABLE)
public void ensureSubscription(long userId) {
    if (!subscriptionRepo.existsByUserId(userId)) {
        subscriptionRepo.save(new Subscription(userId));
    }
}
// One transaction will get a serialization error → caller must retry
```

### Cost tradeoff
Higher isolation = more locking/snapshot overhead = lower throughput.
- `READ UNCOMMITTED` — almost never used, dirty reads are dangerous
- `READ COMMITTED` — default in PostgreSQL, Oracle, SQL Server. Right for most work
- `REPEATABLE READ` — use deliberately for long-running reads
- `SERIALIZABLE` — use sparingly, always implement retry logic for serialization failures

**Key distinction READ COMMITTED vs REPEATABLE READ:**
- `READ COMMITTED`: each query sees latest committed data *at that moment* → data can change between queries in the same transaction
- `REPEATABLE READ`: entire transaction sees a single snapshot from start → consistent across all queries

## Interview Sound Bites

**"How do you find a slow query?"**
> Enable slow query log, then `EXPLAIN ANALYZE` the query. I look for sequential scans on large tables, high actual-vs-estimated row count misalignment, and nested loop joins on big result sets.

**"When would you use SERIALIZABLE isolation?"**
> Financial transfers or any operation where read-then-write correctness is critical and I can't use a simpler explicit lock. The cost is higher contention and potential serialization failures that need retry logic.

**"What's a covering index?"**
> An index that includes all columns a query needs, so the engine answers the query from the index alone without touching the heap (index-only scan). Useful for high-frequency read queries on wide tables.

**"Pessimistic vs optimistic locking — when do you choose?"**
> Pessimistic for financial operations with high contention where the second transaction must wait and succeed. Optimistic for low-contention scenarios like document editing where retrying on conflict is acceptable and you want to avoid lock overhead.

**"How do you prevent deadlocks?"**
> Consistent lock acquisition order — always lock the lower ID first. Plus a lock timeout as a safety net so deadlocks surface as errors rather than hanging threads.
