## Complete Answer

### Confirm with GC logs first:
```bash
# Java 9+
-Xlog:gc*:file=gc.log:time,uptime,level

# Java 8
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log
```
Look for long `Pause Full` entries matching your spike timing.

### Other useful flags:
- `-XX:+HeapDumpOnOutOfMemoryError` — auto heap dump on OOM
- `-Xms` == `-Xmx` — prevent heap resizing which triggers extra GCs

### Two most common root causes of frequent Full GC:
1. **High allocation rate** — tight loops, n+1 queries, creating many short-lived objects
   → floods Young Gen → premature promotion to Old Gen
2. **Old Generation accumulation** — long-lived objects (static caches, session state) fill Old Gen
   → Full GC triggered when Old Gen exhausted

### Fixes:
- Bound caches with eviction (Guava/Caffeine, or LinkedHashMap with max size)
- Review unbounded static collections
- Reduce object creation in hot paths (reuse, pooling)

## Questions & Answers

### We are seeing occasional 5-second freezes in our Ignition gateway during peak data ingestion from IoT devices. How would you determine if this is caused by Garbage Collection, and what specific JVM flags or logs would you look at to diagnose the exact cause?

**Ideal Answer:**
While tools like Grafana are great for high-level monitoring, the most direct way to confirm a 5-second GC pause is to analyze the JVM's Garbage Collection logs. I would enable GC logging in production using `-Xlog:gc*:file=gc.log:time,uptime,level` (Java 9+) or `-XX:+PrintGCDetails -XX:+PrintGCDateStamps` (Java 8). 

I would look specifically for "Stop The World" (STW) pauses and check if the pause time matches the 5-second freeze. I would also determine if it's a Minor GC (Young Gen filling up) or a Full GC (Old Gen exhausted). If it's a Full GC, a heap dump would then be useful to see what objects are retaining memory and not being collected. It's also important to note that PermGen was removed in Java 8 and replaced by Metaspace.

**Key points:**
* Mention enabling and checking GC logs directly via JVM flags (`-Xlog:gc*` or `-XX:+PrintGCDetails`)
* Mention looking for Stop The World (STW) pause times
* Distinguish between Minor GC and Full GC as the cause
* Mention heap dumps as a secondary step to find memory leaks if Full GC is the culprit

**Common mistakes:**
* Relying only on Grafana (doesn't show exact STW pause times well)
* Mentioning PermGen (outdated since Java 8, replaced by Metaspace)
* Assuming heap dumps show GC pauses (heap dumps show memory state, not GC behavior)
